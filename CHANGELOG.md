# Changelog

## Unreleased

### New
- **Syntax version**: `QSP 5.9.5` at the bottom right of the status bar (and `qsp.syntaxVersion`) says which QSP library the game is written for, and clicking it picks the other one; the choice is saved in the workspace settings, and every file is checked again by its rules. `5.9.5`, the last release, is the default; `5.9.6 (dev)` is the library's development version, followed until it is released. The constructs of 5.9.6 are errors in 5.9.5 (the new check `qsp.diagnostics.unsupportedSyntax`): the undefined value `?`, `INSVAR`, `ARRKEY`, `ALIAS`, unary plus, a space after `@` or `@@` (until now a syntax error in every version), a tab before the `_` that joins lines. In 5.9.6 a variable without a prefix holds a value of any type, so `x = 'text'` and `$y = x` are no type mismatch; `COUNTOBJ('key')` counts the objects of that name; a name with `\`, `;`, `^`, `@` or `?` in it is an error, since 5.9.6 ends a name there, and so is a variable named `alias`; `systemVariablePrefix` is off, since 5.9.6 reads a system variable as the type it needs. Hover and completion describe the builtins as the chosen version has them (`OBJ` tells whether there is such an object in 5.9.6, `KILLVAR` without arguments keeps the locals), and completion offers `INSVAR`, `ARRKEY` and `ALIAS` only in 5.9.6. The MCP server follows the workspace's setting. Suggested by Aleks Versus.
- `ALIAS a, $b = 'arr1', 'arr2'` (QSP 5.9.6) is read as a statement: `a` and `$b` are locals that share the arrays `arr1` and `arr2`. `alias` stays a variable when no name follows it (`alias = 1`), as in 5.9.5, and so do `insvar` when it is assigned to (`insvar = 1`) and `arrkey` when no argument follows it (`x = arrkey + 1`), which were read as the new builtins and broke such lines. Which array a name shares isn't followed yet ([TODO.md](TODO.md)).
- A new check, `qsp.diagnostics.systemVariablePrefix` (a warning, on by default), flags a system variable written with a prefix of another type than it holds: a number (`usehtml`, `nosave`, `bcolor`…) as `$usehtml` or `%usehtml`, text (`onnewloc`, `usercom`, `fname`…) as `fname` or `#fname`. QSP 5.9.5 ignores a value of the other type, so what is written is not what the player reads. A name in a string (`killvar '$bcolor'`), a local of that name and `args`/`result`, which hold any type, are left alone. Reported by Aleks Versus.
- The newest QSP library's additions, as its grammar (`qsp_grammar.peg`, now in step with upstream) describes them: `?` alone is the undefined value (`$x = ?`, `if $a = ?`), no longer a variable named `?` used but never assigned; `INSVAR [$name], [value], [index], [#new position]` inserts into an array; `ARRKEY([$name], [#position])` gives an element's key. Names keep `@`, `\`, `;`, `^` and a `?` among other letters (`?abc`), as 5.9.5 reads them. Reported by Aleks Versus.
- **QSP: Export Anonymized Skeleton…** writes a copy of the whole game with only its structure left, for reproducing a problem of the analysis in a game that can't be shared: names renamed word by word with one pseudonym across the game (`room_12` → `wabc_12`, `'room_'` → `'wabc_'`), other text masked to x-es of the same length, numbers, code and the code in strings kept, files renamed `f01.qsps`…. The analysis finds the same locations, jumps and diagnostics in it as in the game (checked on three catalog games and a 12.8 M-character synthetic one). The table of pseudonyms is saved beside the skeleton's folder, for the user only. `npm run stress:skeleton` does the same from the command line.
- **QSP: Add Anonymized Code to Crash Report** adds the anonymized code of the location the server stopped on to a crash report saved earlier, when the offer to add it was passed by. The anonymized code now keeps the structure of strings and comments, their letters masked: quotes, braces, markup, `exec:` links and `<<…>>` interpolations (whose code is anonymized as code), as the analysis reads them.
- How locals pass through calls is worked out in one pass per name over the cycles of calls instead of following every call path, and an edit that changes which locations a location calls with locals in scope works it out again only for the names that can reach that location: on a 12.8 M-character game it takes 1 s instead of 5.1 s on start, and such an edit's aggregates 1.6 s instead of 5.7 s (a synthetic 1500-location game where every location reaches the others: 1.3 s instead of 7.2 s). What the checks read of it is unchanged; hover and the warnings list the first providers in the order of the calls instead of the order they were found in.
- Sticky Scroll keeps the `if`, `elseif`/`else`, `act`, `loop` and label lines around the cursor at the top of the editor too, not only the location and action: it is built from the folding ranges in QSP files (`editor.stickyScroll.defaultModel`, set for `[qsp]`). Each branch of an `if` folds on its own, and so does the part of a block under each label (up to the next label, branch or end). VS Code keeps at most 5000 folding regions per file and drops the deepest nesting levels past that, so in a large single-file game the blocks inside locations don't fold or pin (README, **Folding and Sticky Scroll**). Click a line there to jump to it, or bind **Go to Parent Fold** (`editor.gotoParentFold`) to a key.
- Every file is now analysed one location at a time, open or closed and whatever its size, so a file shows the same symbols and warnings either way, a syntax error in one location no longer affects the others, and an edit re-parses only its location. The status bar's "Per-location parsing" and "Large file" states are gone with the whole-file parse they described.
- Opening a file that was analysed before, by the project or in an earlier session, reuses that analysis and parses nothing up front: a location is parsed when its highlighting or folding is asked for, the visible lines first (a 12.8 M-character file: diagnostics after 3 s instead of 23 s). A file that stays open between sessions is stored in the cache too.
- An unchanged project reads how locals pass between locations from the analysis cache instead of working it out again, when that took long: on a 15.6 M-character game in 10 files, its aggregates take 0.9 s on start instead of 6.6 s.
- The aggregates an edit rebuilds take a third of the time and memory they did (on a 15.6 M-character game in 10 files: 0.5 s and ~70 MB of garbage instead of 1.5 s and ~260 MB).
- An edit that changes code but not the calls that pass locals (a value, a condition) works out again only the variables whose passing it changes, not all of them: on a 15.6 M-character game in 10 files the aggregates take 1.5 s instead of 5 s.
- An edit that changes nothing other locations can see (game text, comments, new lines) no longer works out again how locals pass between locations through calls: on a 15.6 M-character game in 10 files, an edit is checked in 1.9 s instead of 7 s; the same holds for a file open outside a project.
- Editing a word in a list kept in a variable (`local $names = { Ann, Bob }`) no longer diagnoses every project file again: the text of an assignment is shown by hover only, and no longer counts as something other files see (on a 20 MB game in 4 files, such an edit is checked in 5.5 s instead of 13 s).
- The server keeps answering (hover, the visible lines' highlighting, navigation) while it works out the aggregates and diagnostics of a large game: they run a slice of about 20 ms at a time instead of all at once (a 12.8 M-character file: the visible lines' highlighting waits 33 ms instead of 6 s). The file an edit changed is diagnosed before the others, and an edit made meanwhile stops the work for the one before it (a changed value on a 20 MB game in 10 files: its file is checked in 2 s instead of 5.2 s).
- In a project, an edit that changes nothing other files can see (game text, comments, new lines) no longer diagnoses every file again, only the edited one; nor does opening or closing a file (on a 15.6 M-character game in 10 files, an edit is checked in 7 s instead of 11 s).
- An analysis read back from the cache takes less memory than a fresh one instead of more (a 12.8 M-character file: 212 MB instead of 293 MB; a fresh analysis of it, 230 MB instead of 243 MB).
- Closing a project file whose text is unchanged on disk keeps the editor's analysis of it instead of analysing it again (seconds for a large file).
- **Analysis cache**: each project file's analysis is kept on disk (VS Code's workspace storage) and read back when the file hasn't changed, and an unchanged project shows the diagnostics it had last time at once, replacing them when the cross-file analysis has run, so a project opens much faster the second time (on a 20 MB game, diagnostics after 5.4 s instead of 36 s). `qsp.cache.enabled`, **QSP: Clear Analysis Cache**.
- **QSP Libraries** view: install, update and remove libraries from `libraries.json` catalogs (`qsp.libraries.sources`), with checksums, requirements, and a check against the game's location names before anything is written ([LIBRARIES.md](LIBRARIES.md)).
- A build (**Run**, **Export**, MCP `qsp_build`) stops when two locations share a name and lists every place: a player would reach only one of them.
- Libraries listed under `libraries` in `txt2gam.json` (sources in `libs/`) are built into `.qsp` files of their own for `inclib`, never into the game's, in `libs/` beside the game's `.qsp` (so `inclib 'libs/<id>.qsp'` finds them when `outputFile` is in a folder).
- Every diagnostic has a code: the name of its check's `qsp.diagnostics.<code>` setting (`syntax` for syntax errors), shown in the Problems panel and returned by the MCP `qsp_diagnostics`. Outdated built-ins get their own setting, `qsp.diagnostics.deprecatedBuiltins`.
- `!@qsp-ignore` comments silence a check where its finding is intended: on the next line, on their own line after `&`, in the location (`!@qsp-ignore-location`) or in the file (`!@qsp-ignore-file`), for every name or only those after `:`. A misspelled check is reported.
- Quick fixes on a diagnostic: ignore it on this line or in this location (they write the `!@qsp-ignore` comment), or turn its check off in the workspace settings.
- Files in `libs/` show errors only (no warnings about a library's unused locations or variables), and a duplicate location names the library it clashes with.

### Fixes
- The hover and completion of `DESC` showed its argument as optional (`DESC([$location])`); QSP requires it, as the argument count check already said: `DESC($location)`.
- `ARRITEM` with one argument is a warning in 5.9.5, whose `ARRITEM` reads a second argument all the same; 5.9.6 gives the first element.
- A `loop`, `if`, `elseif` or `act` header that doesn't parse names what is missing instead of always a colon: `loop while i<9 step:` reports `Expected a statement after 'step'`, `loop :` `Expected 'while' and a condition after 'loop'`, `loop while :` `Expected a condition after 'while'`, `if : pl 1` `Expected a condition after 'if'`, `act :` `Expected an action name after 'act'`. `Missing ':'` is left for a header that has everything but the colon. Reported by Aleks Versus.
- `#obj` and `#loc` are known: the library declares `OBJ` and `LOC` as functions that give a number (true or false), so they take the numeric prefix like any such function, instead of being reported as unexpected syntax. Reported by Aleks Versus.
- `obj` and `loc` with the name in parentheses (`loc('room')`, `#obj('key')`) count as a use of that location or object, as they did without parentheses.
- In the instant (TextMate) highlighting, the code of an `exec:` link ends with its `href` value, as the analysis reads it, instead of at `</a>`: a string that opens `<a href="exec:…">` and leaves `</a>` to another string (or to none) no longer keeps the link open past its own quote and colours every string after it inside out. Reported by Aleks Versus.
- A `}` in a comment that pairs with no `{` (`! the «}» closes nothing here`) is part of the comment instead of breaking it into syntax errors. Checked on the Sublime Text package's QSP syntax showcase, now part of the tests. Reported by Aleks Versus.
- In the instant (TextMate) highlighting, a comment or the note after `end` inside a `{…}` block ends at the block's closing `}`, as QSP reads it: a block closed on a comment line (`dynamic {*pl a` / `! comment}`) no longer stays open and colours the rest of the file as its code. The note after `end` keeps its braces and quotes, as in a comment. Reported by Aleks Versus.
- Text outside locations (before the first one, between them, after the last) is highlighted as a comment again, and a quote in it no longer opens a string that runs into the next location and colours every string after it inside out: since every file is analysed one location at a time the server sent nothing for that text, and the TextMate grammar coloured it as code. The TextMate grammar now applies code rules only inside a location, from its `#` line to its `--` line, as the location index reads them. Reported by Aleks Versus.
- A server closed with its editor is no longer reported as a crash because its heap once grew fast, while a large game loaded, long before: a run that ended without shutting down is a crash only if something was going wrong at its end (the heap past half its limit, a breadcrumb in its last two minutes, an uncaught error).
- An edit no longer clears the file's problems until it is checked again (half a second later): the Problems panel stopped flickering on every key, and its table view no longer goes empty when the list shrinks under a selected row (a VS Code error, `Cannot read properties of undefined (reading 'element')`).
- A location with many `{…}` blocks nested in blocks kept in variables is analysed in a fraction of the time: finding a node's parent no longer goes through every statement before it each time, and blocks run from other blocks are put in order without searching all of them at each step (800 such groups: 2.6 s instead of 5.7 s).
- `ADDLIB` and `DELLIB`, the old names of `INCLIB` and `FREELIB` besides `ADDQST` and `KILLQST`, are known: highlighted, checked and reported as outdated like those. `CLOSE` without a file (it stops every sound) no longer reports a missing argument, and `DISABLESUBEX` is known as a system variable (unused by players 5.8.0 and later).
- A function that needs no argument (`countobj`, `rnd`, `msecscount`, `$curloc`…) followed by `+` or `-` is added to or subtracted from, as QSP reads it: `if i ! countobj+1` no longer reports `Function 'countobj' expects 0 arguments, got 1 argument`. Such a function takes an argument only in parentheses.
- A `{…}` block is read the way QSP reads it: its end is found by its braces and quotes, whatever is inside. A block that isn't code (a list of words, `local $names = { Ann, Bob, }`) could break the rest of its location, reporting `local $names = {` as unexpected syntax and the strings on a later line as unclosed, and taking the location's symbols with it; it is now a string until something runs it, with no diagnostics and no variables. The syntax errors of a block that runs, where it stands (`dynamic {…}`, `dyneval({…})`) or through a variable (`dynamic $code`, in this location or another), are errors instead of information.
- A `{…}` block that nothing can run is text: an array index (`$mass[{act}]`, the same as `$mass['act']`), or an operand of an operator whose result is a number (`if $s = {generic}` compares with the text `generic`; `and`, `-`, `no`…). Its words are no longer taken for variables (reported as never assigned) or highlighted as code; only `+` and `&`, which join texts that may be kept and run, leave a block code. A block that isn't code, such as a list of words, is highlighted as a string.
- A `{…}` block passed as an argument (`gs 'show', {generic}`, `dynamic $code, 10, {generic}`, `@show({generic})`) is the text the callee gets as `$args[N]`: it is checked and highlighted as code only when the callee is seen running it (`dynamic $args[N]` in that location, or in the `dynamic {…}` it is passed to). A block passed to code nobody can see is text. A block the callee runs now gets its syntax errors reported, as other blocks that run do. Hover, go to definition, find references, rename and highlights leave such text alone: renaming a variable `generic` no longer rewrites the text `{generic}` passed to a location that only prints it. The highlighting of an open file follows a closed file changed on disk (one that starts or stops running its arguments, or jumping to a location).
- A `{…}` block kept in a variable (`$args['temp'] = {generic}`, `$k = 'a' + {b}`) is the text the variable holds: it is checked and highlighted as code only when something may run the variable, a `dynamic`/`dyneval` that names it (in a string or an `exec:` link too), a copy of it that runs (`$c = $h[1]` then `dynamic $c`), or a location it is passed to that runs its arguments. An element run under a key written out runs only the blocks under that key: `dynamic $args['something']` leaves `$args['temp_<<…>>'] = {generic}` text, a call passes each argument into its own `$args[N]` of the callee, and `$r = $args['k']` takes only that element. `$result` always counts as code. Its words still count as uses, so no new warnings about unused variables, and hover, navigation and rename leave the text alone.
- A block that runs (`dynamic $code`) no longer shows the syntax errors of the blocks inside it, which running it doesn't run: an array key (`$mass[{act}]` was reported as `Missing ':' after 'act'`) or a list of words kept in a variable there.
- A line continuation with spaces or tabs after its ` _` (`if x > 0 _ ` and the condition going on below) was reported as unexpected syntax; QSP trims each line before joining them, so it is a continuation.
- A label whose name has brackets or parentheses (`:i[16]i[16]`) was cut at the first bracket and the rest reported as a syntax error; the name is now the whole rest of the line, as QSP takes it. Unary plus (`'a'++rand(0, 20)++'b'`, `x = +5`) is no longer a syntax error.
- `unusedLocations`, `unusedObjects` and `unusedVariables` no longer report a name the game uses as text: a location, object or variable whose name is written to a variable or passed to a call (`$to = 'hall'` … `gt $to`, `gs 'print', 'list'`), or a location a jump target built from text fits (`gs 'eat<<n>>'`). On games from the QSP catalog most of these reports were of such names.
- A location with a syntax error tree-sitter can't recover from (notes written as plain text in the code, an `if` never closed) lost its variables and jumps, kept only its actions and labels, and turned off the "never used" checks of the whole project; the file was also analysed again on every open instead of read from the cache (a 5 M-character game: ready in 10.9 s instead of 1.6 s). Its symbols are now taken from what was parsed.
- The jump graph's statistics in the log could quote game text: a jump target broken by a comment (`gt $curloc - …`) was described by the text where its operator should be. They now name grammar node types and built-in functions only.
- Folding in files past 500 KB matched `act`/`if`/`loop` lines with `end` lines, so a one-line `if x: …` or `act '…': …` shifted the ranges; blocks now fold by the parse, as in smaller files.
- In files past 500 KB and in closed project files, an action or label a syntax error hid from the parser was missing from the Outline and the checks; it is now taken from the text, as in smaller open files.
- `uninitializedVariables` and `mixedVariablePrefixes` gave different results for a file open in the editor and closed (or past 500 KB): only a small open file had the scopes the checks need, so a value that comes through another variable (`б = а` with `а` never assigned) was missed elsewhere. Every file now gets the scope-aware checks (on a 12.8 M-character file, its diagnostics take 3.9 s instead of 3.0 s).
- A write inside a code block held in a `local` of a nested block (`if`, loop) and run by another location through `dynamic` was reported as never read, and hover didn't show it among the caller's values.
- In files past 500 KB, hover showed no possible values for a local of a nested block that takes its value from another variable (`local y = i` in a loop body): scopes were recorded by the parse tree's node ids, which mean nothing in the location's next parse.
- In a project, a large open file (past 500 KB, parsed location by location) showed no syntax errors at all, and closed files could lose theirs after an edit elsewhere.
- A line starting with `--` between locations (an ASCII table, a divider) no longer breaks the highlighting and reports false syntax errors in the rest of that text: only a `#` header starts something there. Reported by Aleks Versus.

## 0.3.0

### New
- **QSP Locations** view in the Explorer: every location of the project, by file or A→Z, with error counts, the start location marked, following the cursor, and rename / duplicate / delete / find references from its context menu.
- **Jump Graph** (**QSP: Show Jump Graph**, `Ctrl+K J`): who jumps to or calls whom, in a tab beside the editor. Around a location, the whole project, or folded by file; hubs hidden, search, hover highlight, click to open a location or the place a jump is written.
  - Dynamic jumps (`gt $next`, `gt 'room_' + n`, `gt $args[0]`, `gt func('pick')`) get **possible** arrows to the locations their variables are known to name, from the nearest write before the jump, the writes before the calls into its location, or every write in the project. Nothing is run; what can't be known still goes to a **?** node.
  - Large games stay usable: a force layout in slices for ~1000 locations, arrows drawn on demand past 5000, and layout that keeps going while the panel is hidden.
- **MCP server** for AI agents: the editor's diagnostics, symbols, references and project information as MCP tools (see [MCP.md](MCP.md)); offered to VS Code agents, and **QSP: Copy MCP Server Config** for other clients.
- **Analysis status** item next to QSP in the status bar: what the server is doing, and degraded modes (**Limited mode**, **Per-location parsing**, **Reduced analysis**).
- **Crash reports**: if the language server stops unexpectedly, a report with numbers and neutral names (never game text) is saved to `.qsp/crash-reports/`, optionally with the anonymized code of the location it was stuck on (`qsp.crashReports.*`).
- Builds: per-file build mode, a configurable main file, the player executable in `txt2gam.json`, and unchanged `.qsp` files are no longer rewritten.
- Syntax errors of project files that are not open are reported.

### Large games
- Games of 1000–1500 locations (25–50 million characters) load without running out of memory: parsing is 8–12× faster, the analysis keeps within bounds on shared local names and deep call graphs, and past 70% of the heap the server drops optional analysis (**Reduced analysis**) instead of crashing.
- `qsp.diagnostics.maxPerFile` (5000) caps the diagnostics of one file.
- `[perf]` lines in the server log give each slow phase's time and memory, without names (`qsp.debug.performanceLog` logs every phase).

### Fixes
- A server crash and parse corruption on some inputs; blocking file I/O and stale trees in project mode; cache invalidation bugs; WASM memory leaks.
- Multiline expressions: operators at the start of a line, line continuations, and a newline before the closing bracket after a multiline `or`.

Earlier versions: see the [GitHub releases](https://github.com/QSPFoundation/qsp-lsp/releases).
